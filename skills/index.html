Skills are recipes you hand the agent.

A skill is a little folder with a SKILL.md file. It teaches Agent a repeatable way to do one job, so you do not re-explain the same process every chat.

The honest version

Chat is a conversation. A skill is a playbook.

You can tell Cursor the same studio rules every week. That works until you forget a step. A skill stores the steps. The agent reads them when the job matches, or when you type /skill-name.

Skills are not magic extra models. They are files. Cursor still uses whatever model you already picked. The skill only changes how the agent approaches the task.

Rules, skills, and just talking

Pick the smallest tool that fits. Do not make a skill for “use TypeScript.”

Just say it

One-off asks. “Make the tile teal.” “Fix this typo.” No file needed.

When: you will not need those steps again.

A rule

Short always-on taste. “No em dashes.” “Keep the hub static.” A few lines, not a procedure.

When: a constraint should follow you around.

A skill

A multi-step workflow. Deploy. Audit. Add a new artifact the same way every time.

When: you keep re-teaching the same process.

What a skill is actually useful for

A skill earns its folder when you would otherwise paste the same 8 steps into chat again. Short taste (“no em dashes”) stays a rule. A procedure becomes a skill.

The same studio job, every week

Add a hub artifact the same way. Ship a cycle build. Turn desk-crit notes into a talking page. That is this class in a nutshell, and why /learn-vibe-artifact already lives in this repo.

Your voice, on purpose

Rewrite in how you actually talk. Keep a sounding-board tone. Format an assignment without inventing a brand. Skills are good when “how it should sound” is a process, not a vibe you hope the model remembers.

A checklist before you call it done

Links work. Hub tile is wired. Contrast is readable. Nothing got deleted. People write skills for “ship checks” so Agent does the boring pass the same way every time.

Tests, PRs, and “how we do this here”

Write tests the repo’s way. Split a giant diff. Draft a PR. Run TDD. Cursor’s own docs use examples like deploy-to-staging and React component patterns, because those are procedures with a beginning, middle, and end.

A careful review pass

Security, bugs, “did the agent just hallucinate a button.” You can write your own review skill, and Cursor already ships ones people type a lot: /review, /review-bugbot, /review-security.

The tool itself

Make a rule. Make another skill. Change a Cursor setting. Draw a canvas next to chat. You do not have to invent those. They are already installed. Type / and they show up.

Skip a skill when the job is tiny. “Make this heading smaller” is chat. “Every new page gets a README, a hub tile, and a distinct theme” is a skill. Named skills (Impeccable, etc.) · Built-in list

The design-skill kind (yes, that one)

A lot of people keep a skill that is basically “design this website this way.” Not “make a site.” A look. Type, color, spacing, motion, what to refuse (generic AI purple gradients, Inter-on-white, three identical cards).

A look

Editorial magazine. Brutalist campus flyer. Candy-pink pet. 90s zine. The skill holds the aesthetic so Agent does not reinvent “clean startup” every chat.

Famous public example: Anthropic’s frontend-design skill, built to dodge generic AI UI.

A system

Tokens, type scale, button and card recipes, “only these CSS variables.” Cursor’s docs use React component patterns scoped to **/*.tsx as the textbook version of this.

When: you are building many pages that should feel like one product.

This project’s face

Hub tiles, paper background, no clone of the neighbor artifact. A class skill can say “new pages get their own palette” the same way a startup skill says “use our brand kit.”

Tip: turn it into a Custom Mode so the look stays on for the whole design session.
